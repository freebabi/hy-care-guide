# 직원 개인 데이터·권한 분리 보안 검토 (USER_DATA_SECURITY_REVIEW)

작성: 2026-11-11
**분류 표기**: 🟢 개발 완료 · 🟡 추가 개발 필요 · 🔵 병원 정보팀 확인 필요 · 🔴 병원 보안 승인 필요

## 한눈에 보기 (쉬운 설명)

- 직원 한 명 한 명의 즐겨찾기·최근 본 자료·자료 묶음·활용 기록·공지 읽음은 **그 직원의 사번에 연결된 별도 파일**에만 저장됩니다. 다른 직원이 보거나 고칠 수 없다는 것을 **실제로 시도해 확인**했습니다(같은 이름의 다른 직원, 남의 묶음 번호를 알아낸 경우 포함).
- 이 앱에는 **환자 이름·등록번호·생년월일·연락처를 저장하는 곳이 없습니다.** 자료 묶음 제목·설명에 환자 정보처럼 보이는 숫자(주민등록번호·전화번호)를 쓰면 **저장이 거부**됩니다.
- 관리자가 보는 전체 통계에는 **직원 이름이 나오지 않고 합계 숫자만** 나옵니다.
- 아직 남은 큰 위험은 두 가지입니다: ① 직원 로그인이 사번·이름만으로 되어 있어 남의 사번을 아는 사람은 그 직원 데이터를 볼 수 있음(AUTHENTICATION_REVIEW 참고), ② 서버 파일 저장 방식의 백업·다중 서버 문제(DATABASE_ARCHITECTURE_REVIEW 참고).

## 1. 저장하는 데이터와 민감도

| 데이터 | 내용 | 개인정보 해당 | 누가 볼 수 있나 |
|---|---|---|---|
| 직원 등록부 | 사번, 이름, 처음·최근 로그인, 로그인 횟수 | **직원 개인정보**(이름·사번) | 관리자(등록 직원 목록) |
| 직원 로그인 기록 | 이름·사번·시각 | 직원 개인정보 | 관리자(화면에는 이름·시간만) |
| 즐겨찾기·최근 본 자료 | 콘텐츠 ID·제목·시각·횟수 | 직원의 업무 행동 기록 | **본인만** |
| 자료 묶음 | 제목·설명·콘텐츠 순서 | 직원이 직접 입력한 글(환자 정보 금지) | **본인만**(공개 범위는 `private`뿐) |
| 활용 이력 | 열람·다운로드·인쇄 준비·구성·안내 제공 기록·문구 준비 | 직원의 업무 행동 기록 | **본인만**. 관리자는 합계 통계만 |
| 공지 읽음 | 공지 ID·읽은 시각 | 직원의 행동 기록 | **본인만**(다른 직원·관리자 모두 개별 열람 불가) |
| 관리자 활동 기록 | 관리자 사번·동작·대상 ID·시각 | 관리자 업무 기록 | 서버 파일(앱 화면에 목록 없음) |
| 공지 | 제목·본문(관리자가 작성) | 환자 정보 금지(안내문) | 게시된 것은 전 직원 |
| **환자 정보** | **저장하지 않음** | — | — |

## 2. 개인별 분리 — 어떻게 지키는가

1. **서버가 사용자 ID를 정합니다.** 세션 쿠키(서명됨)의 사번에서 만든 `emp-<사번>`이 사용자 ID입니다. 브라우저가 보낸 ID·역할·이름 값은 어디에서도 읽지 않습니다.
2. **파일 이름이 곧 사용자 ID**입니다(`users/emp-<사번>.json`). 서버 코드는 항상 "내 ID의 파일"만 열기 때문에, 요청 내용에 다른 직원의 값이 들어 있어도 다른 직원 파일에 닿을 수 없습니다. 파일 경로가 저장 폴더 밖을 가리키지 못하게 막는 검사도 있습니다.
3. **이름으로 데이터를 찾지 않습니다.** 같은 이름의 직원이 여러 명이어도 사번이 다르면 완전히 다른 계정입니다.
4. 남의 묶음 번호를 알아내도, 묶음은 **내 파일 안에서만** 찾기 때문에 수정·삭제가 **404**로 거부됩니다.
5. DB로 옮길 경우에도 모든 개인 데이터는 사용자 고유 ID로 연결하고, 사용자 삭제 시 함께 삭제하도록 설계합니다.

### 확인 결과 (자동 점검, 임시 환경·가짜 직원)
| 확인 | 결과 |
|---|---|
| 직원 B가 직원 A의 즐겨찾기·최근·묶음을 볼 수 있나 | **볼 수 없음** (빈 목록) |
| **같은 이름·다른 사번**(동명이인)이 서로의 데이터를 볼 수 있나 | **볼 수 없음** |
| B가 A의 묶음 번호로 수정/삭제 | **404 거부**, A의 묶음은 그대로 |
| 요청 본문에 `uid`/`userId`를 넣어 남의 ID로 위장 | **무시됨** |
| B의 공지 읽음이 A의 미읽음 수에 영향 | **영향 없음**(각자 계산) |
| 공지 응답에 다른 직원의 읽음 정보 포함 | **없음** |
| 사번 등록 초기화 후 같은 사번으로 다시 로그인하면 데이터 | **그대로 이어짐**(사번 기준 증명) |
| 사용자 파일 이름 | 모두 `emp-<숫자>.json` (이름 없음) |

## 3. API 권한 표 (서버에서 검증)

| API | 비로그인 | 일반 직원 | 관리자 |
|---|---|---|---|
| `GET /api/me/library`, `activity` | 401 | 본인 것만 | 본인 것만 |
| `POST /api/me/favorites·recent·bundles·activity`, `DELETE …` | 401 | 본인 것만 | 본인 것만 |
| `GET /api/notices`, `/notices/[id]`, `unread`, `POST …/read` | 401 | 게시된 공지만(임시 저장 공지는 404, `?all=1`은 무시) | 전체 상태(`?all=1`) |
| `POST/PUT/DELETE /api/notices…` | 401 | **403** | 허용(+활동 기록) |
| `GET /api/admin/usage` (전체 통계) | 401 | **403** | 합계 숫자만 |
| `GET /api/admin/employees`, `DELETE …/[사번]` | 401 | **403** | 허용(+활동 기록) |
| `GET /api/auth/login-log` | 401 | **403** | 허용 |

값을 바꾸는 요청(POST/PUT/DELETE)은 **같은 사이트에서 온 요청인지(Origin)** 도 확인하고, 다른 사이트에서 온 요청은 403으로 거부합니다. 활동 유형 중 열람·구성은 **서버가 직접 기록**하고, 화면이 보낼 수 있는 유형은 4가지로 제한되어 **'발송 완료' 같은 기록을 위조할 수 없습니다**.

## 4. 환자 정보 보호 조치

- 환자 이름·등록번호·생년월일·연락처를 받는 입력칸이 **없습니다**.
- 자료 묶음 제목·설명, 안내 제공 기록은 **일반 안내자료 이름과 시각**만 저장합니다. 화면에 "환자 정보를 입력하지 마세요" 안내가 있습니다.
- 서버가 제목·설명에서 **주민등록번호·전화번호 형태의 숫자**를 발견하면 저장을 거부합니다(자동 점검으로 확인). *한계: 이름·진단명처럼 숫자가 아닌 환자 정보까지는 막지 못합니다 → 안내와 교육이 필요.*
- 활용 이력은 **외부 발송을 하지 않으므로 환자 연락처가 필요 없습니다.** 전자 발송이 연동되면 채널·콘텐츠·시각·결과·실패 사유만 기록하도록 설계했습니다.
- DB 설계에도 환자 식별 열이 없습니다.

| 로그·기록 과다 누적 | 직원당 활동 3,000건·로그인 기록 5,000건 상한 | 낮음 |
| 관리자 오남용 | 관리자 활동 기록, 직원 읽음·개인 이력은 관리자도 개별 열람 불가 | 감사 기록 열람 화면 없음 🟡 |

## 6. 개인정보 보존·파기 (제안, 🔵🔴 확정 필요)

- 직원 이름·사번·활용 이력은 업무 목적(안내자료 활용 확인) 범위에서만 사용.
- 보존 기간 안: (정보팀·개인정보 담당 확정 필요) 예) 활용 이력 1년, 로그인 기록 6개월.
- 퇴사·부서 이동 시: 사번 사용자 비활성화 후 **사용자 삭제로 개인 데이터 일괄 삭제**(DB 설계에서 연쇄 삭제 검증 완료). 현재 파일 방식에서는 `users/emp-<사번>.json`을 삭제하고 등록 초기화.
- 🟡 보존 기간 자동 정리 기능은 아직 없음(상한 건수만 있음).
