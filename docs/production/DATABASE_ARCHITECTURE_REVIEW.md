# 서버 데이터 저장 구조 검토 (DATABASE_ARCHITECTURE_REVIEW)

대상: HY CARE GUIDE의 서버 저장 데이터(직원 개인 데이터, 공지, CMS 콘텐츠 변경분, 개선 요청)
이 문서는 공개용으로 정리한 일반 기술 문서입니다. 특정 배포 환경의 내부 운영 절차나 접속 정보는 담지 않았습니다.

**분류 표기**: 🟢 개발 완료 · 🟡 추가 개발 필요 · 🔵 운영 환경 확인 필요 · 🔴 병원 보안 승인 필요

---

## 한눈에 보기

- 이 앱은 서버 데이터를 **서버 컴퓨터의 폴더**(환경변수 `APP_DATA_DIR`, 없으면 `.data/`) 안의 **JSON 파일**로 저장합니다. 데이터베이스(DB)는 쓰지 않습니다.
- 서버 프로세스가 **1개**일 때는 안전하지만, **2개 이상이면 쓰기가 서로 덮어써져 기록이 사라질 수 있습니다**(아래 실험).
- 서버리스 환경(예: Vercel)은 파일이 영구 보관되지 않아 **운영에 맞지 않습니다**.
- 관리자가 수정·등록한 안내 콘텐츠와 직원의 개선 요청도 이제 **서버에 저장**되어 모든 직원·환자 화면이 같은 내용을 봅니다(브라우저 저장 방식에서 이전 완료).
- 여러 서버로 운영해야 하거나 감사·백업 요건이 생기면 DB로 옮겨야 하며, 저장 함수만 교체하도록 구조를 분리해 두었습니다.

---

## 1. 현재 데이터 저장 구조 🟢

### 1-1. 무엇이 어디에 저장되는가

| 데이터 | 저장 위치(데이터 폴더 기준) | 형식 |
|---|---|---|
| 즐겨찾기·최근 본 자료·자료 묶음·활용 이력·공지 읽음 | `users/emp-<사번>.json` | 사용자별 JSON 1파일 |
| 공지 | `notices.json` | JSON |
| 사번↔이름 등록부 | `employees.json` | JSON |
| 직원 로그인 기록 | `login-log.jsonl` | 한 줄에 한 건 |
| 관리자 활동 기록 | `admin-audit.jsonl` | 한 줄에 한 건 |
| CMS 콘텐츠 변경분(수정한 기본 안내, 신규 등록분, 의료 검토 상태) | `cms/guides.json` | JSON(변경분만) |
| 개선 요청 | `cms/requests.json` | JSON |
| 첨부 파일 | `cms/files/…` | 파일 |
| 복구 직전 자동 복사본 | `cms/backups/<시각>/` | 파일 |

- **기본 안내 88건은 소스코드에 포함**되어 있고, 서버 파일에는 관리자가 바꾼 **변경분만** 저장합니다.
- 개인 데이터는 사번 기반 고유 ID로 분리되어 저장되며 이름으로 연결하지 않습니다.
- 데이터 폴더는 `.gitignore`에 들어 있어 Git에 올라가지 않습니다.

### 1-2. 쓰기 안전장치

- 임시 파일에 끝까지 쓴 뒤 이름을 바꿔 교체합니다(쓰는 도중 오류가 나도 기존 파일 유지). 교체 직전 파일은 `.bak`으로 남깁니다.
- 같은 파일에 대한 쓰기는 한 줄로 세워 처리하고, CMS 콘텐츠 수정은 버전이 어긋나면 덮어쓰지 않고 거부합니다.
- 저장 파일이 손상되었거나 더 새로운 형식이면 **아무것도 쓰거나 초기화하지 않고** 오류를 알립니다(원본 유지).
- 저장 상태는 실제 쓰기 시험으로 판단해 관리자 화면에 표시합니다(저장 폴더 확인됨 / 임시 저장 / 저장 불가).

### 1-3. 동시 접근 실험 (같은 파일에 동시에 쓰기)

| 상황 | 시도 | 실제 저장 | 손실 |
|---|---|---|---|
| 서버 1개, 동시 300건 | 300 | **300** | 0 |
| 서버 2개, 각 150건 동시 | 300 | **4~10** | 290~296 |
| 서버 4개, 각 75건 동시 | 300 | **78~81** | 219~222 |

- 쓰기 보호(직렬화)는 **한 프로세스 안에서만** 작동하므로, 서버가 여러 개이면 서로의 쓰기를 막지 못합니다.
- 서버 1개 고정으로 운영하면 파일 방식도 쓸 수 있습니다(정기 백업 필수). 실험은 CMS 서버 저장 도입 전의 저장 함수로 측정했으며, 보호 방식의 한계는 같습니다.
- 🔵 운영 환경이 서버를 몇 개 띄우는지는 앱이 확인할 수 없으므로 배포 전에 확인해야 합니다.

### 1-4. 재시작·재배포 후 유지

| 환경 | 재시작 | 재배포 |
|---|---|---|
| 내 PC·자체 서버 | 유지 | 폴더가 유지되면 유지 |
| 영구 저장 폴더를 제공하는 컨테이너 환경 | 유지 | 지정한 폴더에 저장한 것만 유지(🔵 환경별 확인) |
| 서버리스(Vercel 등) | 서버가 켜져 있는 동안만 | 사라짐 |

### 1-5. 백업·복구 🟢

- 자동 백업은 없습니다. 운영 환경이 데이터 폴더를 백업하는지는 환경마다 다르므로 🔵 확인이 필요합니다.
- **관리자 백업·복구 기능**(콘텐츠 관리 화면): CMS 콘텐츠 변경분과 개선 요청을 검증값(checksum)이 든 JSON으로 내려받고, 복구는 미리보기 → 확인 → 적용 순서로 진행합니다.
- 백업에는 비밀값·직원 명단·접속 기록·개인 보관함·요청자 ID가 들어가지 않으며, **개선 요청 첨부 파일은 항상 제외**됩니다.
- 직원 개인 데이터와 접속 기록은 데이터 폴더를 통째로 복사하는 방식으로 수동 백업합니다.

### 1-6. 서버리스 환경 적합성

**부적합합니다.** 파일이 영구 보관되지 않고 인스턴스마다 따로 있어 기록이 사라지거나 서로 다르게 보입니다. 또한 직원 이름·사번이 병원 밖 서버로 나가므로 🔴 보안 승인 없이는 쓸 수 없습니다.

## 2. DB로 옮길 경우의 방안 비교

| 항목 | A. 배포 환경이 제공하는 앱 전용 DB | B. 외부 관리형 클라우드 DB | C. 원내 서버 DB |
|---|---|---|---|
| 기존 코드 재사용 | 높음(저장 함수만 교체) | 중간 | 중간 |
| 개발 난이도 | 낮음~중간 | 중간(키 관리·네트워크 예외) | 중간~높음(서버·계정·방화벽 구성) |
| 동시 사용자 처리 | 충분 | 충분 | 충분 |
| 백업·복구 | 🔵 환경 정책 확인 필요 | 자동 백업(요금제별) | 직접 구성 |
| 보안 승인 | 🔵 직원 정보 저장 가능 여부 확인 | 🔴 직원 개인정보가 외부 클라우드에 저장되므로 병원 보안 승인 필수 | 병원 내부라 상대적으로 유리, 🔵 승인 필요 |
| 운영 부담 | 낮음 | 낮음(관리형) | 높음 |

**권고(병원 내부 우선)**
1. **시범 운영**: 서버 1개 고정 + 영구 저장 폴더(`APP_DATA_DIR`) + 관리자 정기 백업.
2. **정식 운영**: 병원이 승인한 내부 DB(A 또는 C)로 이전. 서버가 여러 개여야 한다면 DB가 필수입니다.
3. 외부 클라우드 DB(B)는 🔴 보안 승인이 전제이므로 마지막 선택지입니다.

## 3. DB 전환 시 지켜야 할 설계 원칙 🟡

- 모든 개인 데이터는 **사용자 고유 ID**로 연결하고 이름으로 연결하지 않습니다. 사용자를 삭제하면 개인 데이터도 함께 삭제됩니다.
- 사번은 앞자리 0이 있을 수 있으므로 **문자열**로 저장하고 중복을 허용하지 않습니다.
- 관리자는 1명으로 고정합니다(서버 설정의 관리자 값과 대조).
- **환자 식별정보(이름·등록번호·생년월일·연락처)를 저장하는 열은 두지 않습니다.**
- 파일의 내용은 DB에 넣지 않고 저장소에 두며, DB에는 경로와 파일 정보만 저장합니다.
- 승인 기록이 없으면 '승인' 상태가 될 수 없도록 제약을 둡니다.
- 전환 절차: 서버를 멈추고 데이터 폴더를 백업 → DB에 스키마 적용 → 데이터 이전 → 건수 대조 → 저장 함수 교체 후 배포. 문제가 있으면 백업한 폴더로 되돌립니다.
- 전환 도구(스키마·이전 스크립트)는 운영 승인 후 작성합니다.
