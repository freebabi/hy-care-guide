# 로그인·인증 검토 (AUTHENTICATION_REVIEW)

작성: 2026-11-11 · 공개용으로 정리한 일반 기술 문서입니다(특정 배포 환경의 내부 운영 절차·접속 정보는 담지 않았습니다).
**분류 표기**: 🟢 개발 완료 · 🟡 추가 개발 필요 · 🔵 병원 정보팀 확인 필요 · 🔴 병원 보안 승인 필요

---

## 한눈에 보기 (쉬운 설명)

- 로그인이 **이름만 입력**하던 방식에서 **이름 + 사번**으로 바뀌었습니다. 같은 이름의 직원이 여러 명이어도 **사번으로 서로 다른 사람**으로 구별되어, 보관함과 이력이 섞이지 않습니다.
- 관리자(서버 설정에 지정한 1명)는 **이름 + 사번 + 관리자 비밀번호**가 모두 맞아야 로그인됩니다. 이 세 가지는 **서버 설정에만** 있고 소스코드에는 적지 않았습니다. 다른 사람이 이름을 입력하거나 화면을 조작해서 관리자가 될 방법은 없습니다.
- **중요한 한계**: 사번과 이름은 *비밀이 아닙니다*. 병원 인사 명부와 대조하거나 개인 비밀번호/원내 이메일 인증을 붙이기 전에는, **남의 사번과 이름을 아는 사람이 그 사람으로 로그인할 수 있습니다.** 이 로그인은 "누구인지 *구별*"하는 장치이지 "본인 *확인*"은 아닙니다. 병원 정보팀과 확인해서 본인 확인 수단을 정해야 합니다.

---

## 1. 현재 로그인 방식 (구현 완료)

### 1-1. 직원 로그인
1. 이름(2~20자)과 사번(숫자 5~10자리)을 입력합니다. *(사번 자릿수 규칙은 🔵 정보팀 확인 후 `src/lib/auth/server.ts`의 한 곳만 고치면 됩니다.)*
2. 서버가 **처음 로그인한 사번**은 입력한 이름으로 등록하고, 이후에는 **같은 이름으로만** 로그인을 허용합니다(이름 비교는 공백·대소문자 무시).
3. 서버가 **서명된 세션 쿠키**를 발급합니다(HttpOnly, 12시간). 쿠키 안에는 사번·이름·역할이 있지만, 서버만 아는 비밀키(`SESSION_SECRET`)로 서명되어 **위조하면 무효**입니다.
4. 사용자 고유 ID는 **사번에서 서버가 만듭니다**(`emp-<사번>`). 화면(브라우저)이 보낸 사번·역할 값은 어디에서도 읽지 않습니다. 브라우저로 내려가는 응답에는 사번이 포함되지 않습니다.

### 1-2. 이름 잘못 입력 시 (복구)
첫 로그인에서 이름을 틀리게 입력하면 그 사번에 틀린 이름이 등록됩니다. 이때는 **관리자가 '직원 접속 기록' 화면의 "사번에 등록된 직원" 목록에서 '등록 초기화'** 를 누르면 풀립니다(보관함·이력은 사번 기준이라 지워지지 않습니다). 이 동작은 관리자 활동 기록에 남습니다.

### 1-3. 로그인 실패 제한
- 직원: **사번별**로 10분에 5번 실패하면 그 사번만 잠시 막습니다.
- 관리자: 같은 IP 5회 또는 전체 합산 30회 실패하면 10분간 막습니다. 어느 항목이 틀렸는지 알려주지 않고 한 가지 문구만 보여줍니다.
- *이유*: 처음에는 IP 기준으로 제한했는데, 병원처럼 모두가 같은 IP로 보이는 환경에서는 **직원 몇 명의 오타가 전 직원을 10분간 막을 수 있어** 사번 기준으로 바꿨습니다(테스트 중 발견·수정).

## 2. 관리자 권한 (PART 5)

| 항목 | 구현 |
|---|---|
| 관리자 수 | **1명**. 서버 설정(`ADMIN_EMPLOYEE_ID`, `ADMIN_NAME`, `ADMIN_PASSWORD`)에 지정된 사람만. 셋 중 하나라도 비면 관리자 로그인은 꺼짐 |
| 관리자 로그인 | 이름 + 사번 + 비밀번호 **모두** 일치해야 함(상수 시간 비교). 틀리면 한 가지 메시지 |
| 권한이 연결되는 곳 | **사용자 고유 ID(사번 기반)**. 세션 확인 때마다 "이 사번이 서버 설정의 관리자 사번인가"를 다시 검사 |
| 일반 직원 | `EMPLOYEE` 권한만. 관리자 사번으로는 직원 로그인이 **거부**됨(관리자 로그인으로 안내) |
| 이름으로 관리자 되기 | 불가. 이름은 권한과 무관 |
| 화면 조작으로 관리자 되기 | 불가. 쿠키의 역할·사번을 바꾸면 서명이 깨져 **로그아웃 상태**가 됨(실험으로 확인). 옛 `localStorage` 값도 효과 없음 |
| 관리자 API | 모든 관리자 API(공지 작성·수정·삭제, 통계, 직원 등록 초기화, 로그인 기록)는 **서버에서** 세션을 검증(`requireAdmin`). 화면의 버튼 숨김은 편의일 뿐 |
| 관리자 활동 기록 | 공지 작성·수정·삭제, 직원 등록 초기화가 `admin-audit.jsonl`에 (관리자 사번, 동작, 대상 ID, 시각)으로 남음. 공지 본문·비밀번호는 기록하지 않음 |
| 화면 표시 이름 | 화면에는 고정된 부서 표시 이름을 사용합니다. 실제 이름·사번은 로그인 확인에만 쓰고 화면·응답에 노출하지 않음 |
| 개인정보 취급 | 관리자 이름·사번은 소스코드가 아니라 **서버 설정**(로컬 `.env.local`)에만 있음. 저장소에 올라가지 않음 |

### 검증 결과
- 인증 **44개 검사 모두 통과**: 이름만/사번만 입력 거부, 사번 형식(5자리 미만·문자·공백·SQL 문자열) 거부, 같은 사번 다른 이름 거부, 공백만 다른 같은 이름 허용, 관리자 표시용 예약 이름 거부, 관리자 사번의 직원 로그인 거부, 관리자의 틀린 항목(비밀번호/이름/사번/빈 비밀번호) 모두 같은 메시지로 거부, 관리자 로그인 성공 시 응답에 사번·실제 이름 없음, 쿠키 위조 4종(역할 변경·사번을 관리자로 변경·둘 다·옛 형식) 모두 로그아웃 처리, 위조 관리자 쿠키로 공지 작성 시 401, **동명이인(같은 이름·다른 사번)은 서로 다른 계정으로 데이터가 분리**, 직원의 관리자 API 호출 403, 사번 등록 초기화 후 **데이터가 사번 기준으로 그대로 유지**, 사용자 파일 이름이 `emp-<사번>.json`(이름 아님), 감사 기록 내용, 반복 실패 429, 교차 출처 요청 403.
- 기능 점검 **86개 중 85개 통과**(1개는 점검 스크립트의 기대값 오류, 앱 결함 아님).

## 3. 한계와 위험 (솔직한 평가)

| 위험 | 설명 | 심각도 |
|---|---|---|
| 사번·이름은 비밀이 아님 | 사번과 이름을 아는 사람이 **그 사람으로 로그인**할 수 있음(직원 로그인). 그 직원의 보관함·이력을 볼 수 있음. 다만 환자 정보는 앱에 없고, 보이는 것은 즐겨찾기·열람 이력·공지 읽음 수준 | 중간 |
| 선점 등록 | 아직 로그인한 적 없는 직원의 사번을 다른 사람이 먼저 입력하면(틀린 이름으로) 그 사번이 먼저 등록됨 → 본인은 막힘(관리자가 초기화로 해결) | 낮음~중간 |
| 인사 명부 미연동 | 존재하지 않는 사번도 로그인 가능 | 중간 |
| 서버 메모리 방식 실패 제한 | 서버를 다시 시작하면 제한이 초기화되고, 서버가 여러 대면 대수별로 따로 셈 | 낮음 |
| 비밀번호 보관 | 직원 비밀번호는 없음(저장할 비밀번호가 없어 유출될 비밀번호도 없음). 관리자 비밀번호는 서버 설정에만 | — |

> 병원 안 네트워크나 사내 앱 플랫폼의 접속 승인 기능(승인된 직원만 접속)이 **첫 번째 관문**이 되면 위 위험이 크게 줄어듭니다. 이 앱의 로그인은 그 안쪽의 **구별·권한 분리** 장치로 쓰는 것이 안전합니다.

## 4. 더 안전하게 만드는 방법 비교 (병원 정보팀과 결정 필요)

| 방법 | 설명 | 장점 | 단점/필요한 것 |
|---|---|---|---|
| ① 플랫폼 접속 승인 활용 | 사내 앱 플랫폼에서 앱을 **비공개**로 등록해 승인된 직원만 접속 | 추가 개발 거의 없음, 승인·접속 기록은 플랫폼이 제공 | 🔵 승인 절차·담당자 지정. 앱 안의 로그인은 여전히 이름+사번 |
| ② 포털이 알려주는 직원 정보 사용(SSO) | 포털이 로그인한 직원의 사번을 앱에 전달해 주는지 확인 | 직원이 다시 로그인할 필요 없고 사번이 **확인된 값**이 됨 | 🔵 전달 여부를 정보팀에 문의. 전달된다면 `userIdOf()`/로그인만 교체하면 됨 |
| ③ 인사 명부 대조 | 사번↔이름 명부를 앱에 올려 로그인 때 대조 | 존재하지 않는 사번·선점 등록 차단 | 🔵 명부 제공·개인정보 승인, 🟡 명부 가져오기 기능 개발 |
| ④ 첫 로그인 때 개인 비밀번호 설정 | 직원이 본인 비밀번호를 정하고 이후 사번+비밀번호 | 본인 확인 가능, 병원 밖 서비스 불필요 | 🟡 비밀번호 저장(암호화)·재설정 절차 개발, 🔵 비밀번호 정책 |
| ⑤ 원내 이메일 인증 | 원내 이메일로 인증 링크 발송 | 일반적인 본인 확인 방식 | 🔵 메일 발송 서비스 사용 가능 여부(외부·다른 서버 접근이 제한된 환경에서는 불가할 수 있음) |

**권고**: ① 즉시 적용 + ② 가능 여부를 정보팀에 문의. ②가 안 되면 ③ 또는 ④를 추가 개발. (외부 통신이 제한된 환경에서는 외부 인증 서버 연동형 SSO가 불가능할 수 있습니다 🔵.)

### 운영 전 설정 (값은 채팅·저장소에 적지 않음)
`SESSION_SECRET`, `ADMIN_PASSWORD`, `ADMIN_EMPLOYEE_ID`, `ADMIN_NAME` — 로컬은 `.env.local`, 배포 환경은 그 환경의 비밀값 설정 기능에 입력. `.env.example`에 항목만 있고 값은 비어 있습니다.
