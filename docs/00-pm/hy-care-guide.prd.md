# PRD — HY CARE GUIDE (한양 케어가이드) Phase 1

> 이 문서는 별도 기획 단계 없이, 개발 과정에서 사용자와 합의된 요구사항을 기준으로
> 사후 정리한 PRD입니다. Phase 1(EMR-free 환자 안내 콘텐츠 전달 지원 시스템)의
> 범위만 다루며, Phase 2(서버 DB, 인증, 실제 발송 API 연동 등)는 별도 PRD로 다룹니다.

## 1. 배경 및 문제 정의

한양대학교병원 직원은 환자에게 검사·수술·입원·퇴원 등 상황별 안내가 필요할 때마다
문서를 찾거나 구두로 설명해야 해서 안내 품질이 담당자에 따라 들쭉날쭉하다. 반면
"환자정보시스템"을 새로 만들면 EMR/EHR 연동, 개인정보 보호법 준수 등 초기 단계에서
감당하기 어려운 리스크가 발생한다.

**핵심 원칙**: HY CARE GUIDE는 환자 개인정보(이름·등록번호·전화번호 등)를 절대
보유·조회하지 않는다. 환자 식별과 실제 발송은 병원 기존 EHR이 담당하고, 이 서비스는
"전달할 안내 콘텐츠를 찾고 미리보고, 전달용 문구·링크를 준비하는" 역할만 한다.

## 2. 대상 사용자

- **병원 직원**(간호사·원무팀 등): 콘텐츠를 검색해 환자에게 전달할 안내를 준비하는 주 사용자
- **환자**: SMS/QR/카카오로 받은 링크를 클릭해 안내 콘텐츠를 읽는 최종 열람자 (별도 로그인·계정 없음)

## 3. 기능 요구사항

### 3.1 직원용 웹 (4개 메뉴)

| 메뉴 | 경로 | 기능 |
|---|---|---|
| 환자 안내 콘텐츠 | `/` | 50개 콘텐츠를 카테고리(검사/수술/입원/퇴원/기타)·진료과·여정단계·검색어로 필터링, 카드 목록으로 표시 |
| 콘텐츠 관리(CMS) | `/cms` | 콘텐츠 등록·수정·게시/비게시 전환, 목록 검색 |
| 발송 이력 | `/history` | 발송 시각·콘텐츠·채널·완료 여부만 기록된 이력 조회 (환자 식별정보 없음) |
| 통계 | `/dashboard` | 카테고리별·채널별 준비 건수 집계(이번 브라우저 세션 기준) |

### 3.2 콘텐츠 미리보기 → 발송 어시스턴트

- 카드의 "미리보기" 클릭 시 모달로 상세 내용(검사 전/중/후 등 단계별 안내, FAQ, 위치/연락처)을 보여준다.
- "환자에게 보내기"에서 SMS / QR / 카카오 알림톡 3개 채널 중 선택:
  - **SMS**: 문구·링크·전체 내용을 각각 복사할 수 있다.
  - **QR**: 콘텐츠 URL을 인코딩한 QR 이미지를 보여주고, 복사·다운로드할 수 있다.
  - **카카오**: 알림톡 미리보기 문구를 보여주고 복사할 수 있다.
- 세 채널 모두 **실제 발송 API를 호출하지 않는다.** 문구/링크 준비와 복사까지만 지원한다.
- 복사 버튼을 실제로 클릭했을 때만 발송 이력에 1건이 기록된다(단순 열람은 기록하지 않는다).

### 3.3 환자용 콘텐츠 페이지

- 경로: `/c/[slug]` — 콘텐츠별 고정 URL, 만료 없음, **URL 어디에도 개인 식별값을 포함하지 않는다**(쿼리 파라미터 포함).
- 게시 상태가 아닌 콘텐츠는 존재하지 않는 슬러그와 동일하게 "안내를 찾을 수 없습니다"로 처리한다.
- 본문 텍스트는 고령 환자 가독성을 위해 16px 이상으로 표시한다.
- 연락처는 `tel:` 링크로 감싸 클릭 시 바로 전화 연결이 가능해야 한다.
- 카카오톡/문자 미리보기 카드(OG 태그)를 위해 제목·설명·이미지를 서버에서 생성한다.

### 3.4 콘텐츠 데이터

- 카테고리별 최소 수량: 검사 15 / 수술 10 / 입원 9 / 퇴원 8 / 기타 8 (총 50건).
- 각 콘텐츠는 제목, 카테고리/서브카테고리, 진료과, 여정단계, 요약, 주의사항, 전/중/후 안내, FAQ, 위치/연락처, 관련 콘텐츠, 예상 읽기 시간, 게시 상태, 버전, 최종 수정일을 가진다.
- 구체적 수치(금식 시간, 복약 용량 등)가 포함된 항목은 `needsClinicalReview: true`로 표시해, 병원 공식 검토 전 프로토타입 예시임을 명확히 한다.

## 4. 비기능 요구사항

- **PII 제로**: 환자 이름·등록번호·전화번호를 어떤 화면·URL·저장소에도 하드코딩하거나 실데이터로 노출하지 않는다.
- **배포 독립성**: SMS/QR/카카오 링크와 OG 메타태그는 배포 도메인이 무엇이든(로컬/스테이징/실제 도메인) 자동으로 올바른 주소를 가리켜야 한다(하드코딩 금지).
- **반응형**: 모바일(360~430px)·태블릿(768px)·데스크톱에서 가로 스크롤 없이 정상 동작해야 한다.
- **정확한 발송 이력**: 발송 이력·통계는 사용자가 실제로 취한 행동(복사·다운로드)만 반영해야 한다.
- **빌드 안정성**: `npm run lint`, `npm run build`가 오류 없이 통과해야 한다.

## 5. 명시적 제외 범위 (Non-goals, Phase 1)

- 실제 카카오 알림톡 API, 실제 SMS 발송 API 연동
- 환자 목록 조회, 환자별 추천, `/patients/[id]` 등 환자 식별 기반 화면
- 로그인/권한 체계, 서버 DB (Phase 2로 이관)
- EMR/EHR과의 직접 연동

## 6. 성공 기준

1. 50개 콘텐츠가 5개 카테고리 요건대로 등록되어 있고, 전부 `/c/[slug]`에서 정상 열람된다.
2. 직원이 검색→미리보기→발송 어시스턴트(SMS/QR/카카오)까지 막힘없이 조작할 수 있다.
3. 개인정보 노출 검사(이름/등록번호/전화번호 패턴, 하드코딩 예시)를 전수 통과한다.
4. CMS에서 수정한 내용이 저장되고, 같은 브라우저에서 새로고침·환자 화면에 반영된다.
5. 발송 이력·통계가 실제 사용자 행동과 정확히 일치한다(허위/누락 기록 없음).
6. 모바일·태블릿 뷰포트에서 레이아웃 깨짐이나 가로 스크롤이 없다.
7. `npm run lint`, `npm run build`가 모두 오류 없이 통과한다.
